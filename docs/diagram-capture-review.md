# 검토: 문서·웹의 도식을 인식해 hwpx 표로 재현하는 도구

문서(보고서·PDF·발표자료)나 웹에 있는 조직도·체계도·절차도를 **읽어서** 같은 모양의
한글(.hwpx) 표로 다시 그리는 도구를 만들 수 있는지 검토한 결과다. 지금 저장소의
도식 기능(`hwpx_studio/diagram.py`)을 출발점으로 본다.

결론부터: **만들 수 있다.** 다만 한 덩어리로 보면 안 된다. "인식"과 "재현"은 성질이
전혀 다른 문제이고, 재현 쪽은 이미 상당 부분 돌아가는 반면 인식 쪽이 새로 만들 부분이다.
그리고 "원본과 똑같이"는 입력 종류에 따라 되는 정도가 크게 다르다. 아래에 무엇이
확인되었고 무엇이 추정인지 구분해 적는다.

---

## 1. 구조: 세 토막으로 나눈다

```
원본 도식 ─→ [수집기] ─→ 도식 IR(JSON/텍스트) ─→ [렌더러] ─→ hwpx 표
 (그림·SVG·                 구조 + 노드별 색·선          (이미 있음)
  PPTX·웹)                  (새로 정의)
        └────────── 사람이 눈으로 확인·수정하는 지점 ──────────┘
```

가운데에 **사람이 읽고 고칠 수 있는 중간 표현(IR)** 을 두는 것이 이 설계의 핵심이다.
인식은 어떤 방법을 쓰든 틀릴 수 있는데, 중간 표현이 텍스트면 틀린 곳만 한 줄 고쳐
다시 만들면 된다. 이 저장소가 이미 `:::diagram` 블록으로 그렇게 하고 있으므로
새 개념을 들여올 필요가 없고, 확장만 하면 된다.

---

## 2. 이미 되어 있는 것 (재현 쪽)

| 항목 | 상태 | 근거 |
|---|---|---|
| 트리/흐름/격자 → 표 격자 좌표 계산 | 있음 | `diagram.py: build_grid` |
| 셀 한 변 테두리로 연결선 그리기 | 있음, 한글에서 표시 확인 | `prototypes/README.md` |
| 상자 = 여러 열 병합, 연결선은 상자 정중앙 | 있음 | `docs/diagram-guide.md` §4 |
| 폭 초과 시 자동 축소 → 이미지 폴백 | 있음 | `diagram.py: _fit_box_width` |
| **셀마다 다른 배경색** | 파일 형식·API는 지원, 현재 IR이 안 실어 보냄 | 아래 §3 |
| 브라우저(JS) 엔진 동일 동작 | 있음, CI에서 대조 | `tools/compare_js_python.py` |

즉 렌더러는 "구조 + 색"만 제대로 넘겨주면 그릴 준비가 되어 있다.

### 확인 실험

`prototypes/style_capture_poc.py`를 돌리면 노드마다 다른 배경색과 **빨간 점선
연결선**을 가진 hwpx가 실제로 만들어진다. 생성물의 `header.xml`을 열어 본 결과:

```
  id  채움색        선(종류 / 두께 / 색)
   7  #C00000    SOLID/0.3 mm/#000000     ← 최상위 상자
   8  #2E75B6    SOLID/0.3 mm/#000000     ← 노드별로 다른 색
  10  #70AD47    SOLID/0.3 mm/#000000
  11  #FFC000    SOLID/0.3 mm/#000000
  12  -          DASH/0.3 mm/#C00000      ← 점선 연결선
```

`python-hwpx`의 `ensure_border_fill`이 `fill_color`, `border_color`,
`border_width`, `border_type`(SOLID/DASH/DOT/LONG_DASH 등 17종),
`fill_gradient`를 셀 단위로 받고 같은 조합은 재사용한다. **디자인 재현의
하부 구조는 이미 갖춰져 있다**는 뜻이다. 지금 막고 있는 것은 형식이 아니라
IR과 프로파일이 색을 문서 전체 하나로만 정한다는 점이다.

## 3. 무엇까지 닮게 만들 수 있나 (표의 물리적 한계)

hwpx **표**로 도식을 흉내 내는 방식이라, 표가 표현할 수 있는 것까지만 된다.

| 원본의 디자인 요소 | 표로 재현 | 비고 |
|---|---|---|
| 상자 배경색(임의 RGB) | ○ | 확인함(§2 실험) |
| 상자 배경 그라데이션 | ○ | `fill_gradient` 지원, 미검증 |
| 상자 테두리 색·두께 | ○ | 셀 단위로 지정 가능 |
| 점선·일점쇄선 연결선 | ○ | `border_type` 17종 |
| 굵기가 다른 연결선(주선/보조선) | ○ | `border_width` 를 mm로 |
| 글자 색·크기·굵기(노드별) | △ | 형식은 되나 **현재 구현은 2종 고정**(`diagram`, `diagram_root`). 동적 charPr 등록 필요 |
| 셀 하나에서 변마다 다른 색 | △ | OWPML은 변별 속성을 갖지만 `ensure_border_fill`이 한 색만 받음 → 직접 XML 조립 필요 |
| 화살표 머리 | △ | 표 방식은 직선만. `→ ▼` 문자로 대체 중 |
| 둥근 모서리 상자 | ✕ | 표 셀은 직각 |
| 대각선·곡선 연결선 | ✕ | 셀 변은 수직/수평뿐 |
| 도형 겹침·그림자·투명도 | ✕ | |
| 회전한 글자(세로쓰기 라벨) | ✕ | |
| 아이콘·로고 | ✕ | 표 안에 그림을 넣는 기능이 아직 없음 |

**판단**: 관공서·연구원 보고서에 나오는 조직도·추진체계도·전달체계도는 거의 전부
"직사각형 + 직교 연결선 + 단색 채움"이다. 위 표의 ○ 항목만으로 **실무 도식의
대부분은 눈에 띄게 닮게 만들 수 있다**. 반면 마케팅 자료의 곡선·아이콘·입체 도식은
표로 재현할 대상이 아니고, 그 경우 `render=image` 폴백이나 원본 그림 삽입이 맞다.
도구가 이 판정을 스스로 내려 알려 주는 편이 낫다(§6의 "재현 가능성 점수").

## 4. 입력별로 얼마나 정확히 읽히나 (인식 쪽)

여기가 새로 만들 부분이고, 난이도 차이가 크다. **벡터 정보가 남아 있으면 결정적으로
정확하고, 픽셀만 있으면 추정**이다.

| 입력 | 방법 | 구조 | 색 | 난이도 |
|---|---|---|---|---|
| Mermaid / Graphviz 텍스트 | 문법 그대로 파싱 | 정확 | 정확 | 낮음 |
| SVG (웹·문서에서 추출) | `<rect>/<text>/<line>` 좌표 → 포함관계·연결 추론 | 정확 | 정확(`fill` 속성) | 낮음~중간 |
| 웹 HTML/CSS 도식 | 헤드리스 브라우저로 DOM 상자 좌표+계산된 색 추출 | 정확 | 정확 | 중간 |
| PPTX (발표자료) | `python-pptx`로 도형·연결선·채움색 | 정확 | 정확 | 중간 |
| HWPX 안의 그리기 개체 | `hp:rect`/`hp:line` 좌표 읽기 | 정확 | 정확 | 중간 |
| PDF(벡터로 만든 것) | 선·사각형·글자 좌표 추출 후 재조립 | 대체로 정확 | 정확 | 중간~높음 |
| **스캔·캡처 이미지(PNG/JPG)** | 비전 모델이 구조를 읽음 | **추정** | 좌표를 받아 **원본 픽셀에서 직접 샘플링** | 높음 |

마지막 줄이 요점이다. 그림에서 색까지 눈대중으로 받아 적으면 어긋나지만,
**상자의 위치만 받아 그 자리의 원본 픽셀 색을 직접 집으면 색은 정확해진다.**
구조는 추정, 색은 실측으로 나누는 것이 이 문제의 실용적인 해법이다.
(같은 방식으로 선 굵기·점선 여부도 픽셀에서 재는 것이 가능하다 — 미검증)

구조 추정의 정확도는 도식의 복잡도에 좌우된다. 상자 10개 안쪽의 전형적인 조직도는
잘 맞을 것으로 보지만 [추정], 점선 보고선·겹친 그룹박스·범례가 섞이면 사람이
고쳐야 한다. **자동 확정하지 않고 확인을 거치게 하는 설계**가 필요한 이유다.
서식 추출(`extract`)에서 이미 쓰고 있는 원칙과 같다.

## 5. 지금 구조로는 못 그리는 배치 (레이아웃 확장 필요)

실제 조직도에는 지금 `_grid_org`가 다루지 않는 모양이 흔하다.

| 모양 | 예 | 현재 | 필요한 일 |
|---|---|---|---|
| 참모·보조 조직 | 원장 옆에 붙는 감사실 | 자식으로 내려감 | 세로선 중간에서 옆으로 빼는 배치 |
| 점선 보고선 | 협력·자문 관계 | 없음 | 노드 간 임의 연결 + 선 종류 |
| 형제가 많을 때 줄바꿈 | 실·국 12개 | 폭 초과 → 이미지 폴백 | 여러 줄로 접어 배치 |
| 그룹 묶음 상자 | "본부" 테두리로 팀들 묶기 | 없음 | 배경 셀 영역 + 겉테두리 |
| 좌우 대칭 배치 | 중앙-지방 대응 | 없음 | 열 기준 배치 |

폭 한계는 측정해 두었다(`policy-default`, 최대 폭 160mm 기준):

| 같은 단계 상자 수 | 표 크기 | 상자 폭 | 결과 |
|---|---|---|---|
| 3개 | 4행 × 22열 | 28mm | 정상 |
| 5개 | 4행 × 38열 | 25mm | 자동 축소 |
| 8개 | 4행 × 62열 | 15.5mm | 자동 축소(글자 꺾임 우려) |
| 12개 | 4행 × 94열 | 10.2mm | **이미지 폴백** |

즉 **형제가 8개를 넘으면 표 방식이 사실상 한계**다. 한국 부처·기관 조직도는 이
구간에 자주 들어가므로, 줄바꿈 배치는 있으면 좋은 기능이 아니라 필수에 가깝다.
열 수가 100에 가까워지면 한글에서 표 편집이 느려질 수 있다는 점도 감안해야 한다 [추정].

## 6. 만들어야 할 것과 규모

| # | 항목 | 손대는 곳 | 규모 |
|---|---|---|---|
| 1 | 도식 IR에 노드별 스타일 추가(`fill`/`border`/`text_color`/`line_type`) | `diagram.py` | 소 |
| 2 | `emit_grid`가 셀별 색·선종류를 쓰도록 | `diagram.py` | 소 (§2에서 실증) |
| 3 | 노드별 글자색·크기용 동적 charPr 등록 | `engine.py` | 중 |
| 4 | 레이아웃 확장(참모·줄바꿈·그룹·점선 연결) | `diagram.py` | 중~대 |
| 5 | 수집기: Mermaid·SVG·HTML | `capture/` 신설 | 중 |
| 6 | 수집기: PPTX·HWPX 그리기 개체·PDF | `capture/` 신설 | 중~대 |
| 7 | 수집기: 이미지(비전 + 픽셀 색 샘플링) | `capture/` 신설 | 대 |
| 8 | 원본/변환 나란히 보는 확인 화면 | `preview.py`, 웹앱 | 중 |
| 9 | 재현 가능성 점수(표로 될지, 그림으로 둘지 판정) | `capture/` | 소 |
| 10 | 브라우저(JS) 엔진에 1~4 이식 | `docs/js/hwpx-studio.js` | 중 (CI 대조가 있어 누락은 잡힘) |

**주의할 비용**: 이 저장소는 파이썬 엔진과 브라우저 엔진 두 벌을 같은 결과가 나오도록
유지하고 있다(`tools/compare_js_python.py`). 렌더러(1~4)를 건드릴 때마다 이식 비용이
따라붙는다. 반대로 수집기(5~7)는 브라우저에서 돌릴 필요가 없으므로 파이썬 전용으로
두면 이 비용이 없다. **수집기는 파이썬 전용, 렌더러 변경은 최소화**가 유리하다.

## 7. 권하는 순서

| 단계 | 내용 | 확인 방법 |
|---|---|---|
| M1 | IR 스타일 확장 + 셀별 색 렌더(#1~3) | 색 지정 도식을 만들어 한글에서 열어 확인 |
| M2 | Mermaid·SVG 수집기(#5) + 확인 화면(#8) | 웹 도식 5개를 넣어 구조 일치율 확인 |
| M3 | 레이아웃 확장(#4) | 실제 기관 조직도(형제 8개 이상)로 확인 |
| M4 | 이미지 수집기(#7) + 재현 가능성 점수(#9) | 보고서 캡처 20건으로 정확도·수정 횟수 측정 |
| M5 | PPTX·PDF·HWPX 수집기(#6) | 왕복(원본→표→비교) |

M1·M2까지만 해도 "웹/발표자료의 도식을 복사해 한글 보고서에 표로 넣는" 실사용은
가능해진다. 가장 어려운 이미지 인식(M4)은 뒤로 미뤄도 도구가 쓸모 있다는 뜻이고,
검토 관점에서는 이 점이 중요하다.

## 8. 정리: 되는 것과 안 되는 것

**된다**
- 구조(계층·흐름·격자)를 읽어 한글에서 편집 가능한 **진짜 표**로 만드는 것
- 배경색·테두리색·선 굵기·점선을 **상자마다 다르게** 재현하는 것 (형식·API 확인함)
- 벡터 입력(Mermaid·SVG·웹·PPTX)에서는 구조와 색을 **거의 그대로** 가져오는 것

**안 된다 / 조건부**
- 둥근 모서리·곡선·대각선·그림자·아이콘 → 표로는 불가, 그림 폴백이 답
- 스캔 이미지에서 **자동으로, 확인 없이** 정확한 도식을 얻는 것 → 확인 루프 전제
- 형제 8개가 넘는 넓은 조직도 → 레이아웃 확장 전에는 이미지로 밀림

**이 문서에서 실제로 확인한 것**: 셀별 채움색·테두리색·점선이 hwpx 파일에
제대로 들어간다는 것(§2), 형제 수에 따른 표 크기와 폭 한계 수치(§5).
나머지 인식 정확도는 아직 측정하지 않은 추정이다.
